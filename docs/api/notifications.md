# Notifications API

All routes are under `/api/v1/notifications` and require the authenticated
TripBuddy session. List pages contain at most 50 notifications. User-triggered
write operations are limited to 30 requests per user per minute.

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/` | Newest first, paginated; dismissed and expired notifications are omitted. |
| GET | `/unread-count` | Return the persisted unread count. |
| GET | `/preferences` | Return in-app category settings and configured channel capabilities. |
| PATCH | `/preferences` | Update selected in-app categories, e.g. `{ "categories": { "MESSAGES": false } }`. |
| PATCH | `/read` | Mark all active notifications as read. |
| PATCH | `/:notificationId/read` | Mark one recipient-owned notification as read. |
| DELETE | `/:notificationId` | Dismiss one recipient-owned notification. |

Categories currently supported are `CONNECTIONS`, `MESSAGES`, `EXPENSES`,
`PAYMENTS`, and `SAFETY`. In-app delivery can be disabled by category. Email
and push are reported as unavailable and cannot be enabled through this API.
Security-critical account notices are reserved from preference opt-out, but no
such event type is currently generated by this phase.

Every read, dismiss, and preference operation is scoped to the authenticated
recipient. A missing or other user's notification returns not found. Notification
routes are generated from server-side templates and point to pages that perform
their normal authorization checks. The API does not return message text, payment
amounts, expense notes, emergency contacts, or moderator notes.

Notifications expire after 180 days. MongoDB's TTL monitor removes expired
records asynchronously, so expiry is not an exact deletion time. There are no
email, push, SMS, or other external delivery providers configured.
