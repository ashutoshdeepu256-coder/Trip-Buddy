# Maps and location architecture

TripBuddy reuses destination and trip GeoJSON rather than creating a separate geographic database. Destination and trip schemas use `[longitude, latitude]` coordinates and existing `2dsphere` indexes. Nearby destination requests use `$near`; nearby trip discovery uses `$geoNear` as its first aggregate stage, constrained by the established status and privacy match before joining destination, creator and active-member summary data. Nearby trip cards expose only a rounded great-circle distance.

`maps.service` is the server provider boundary. Mapbox Geocoding v6 forward/reverse lookup and Directions v5 routing are enabled only by `MAPBOX_SERVER_TOKEN`; requests use a bounded AbortController timeout, minimized output, safe upstream errors and a per-client rate limit. Geocoding responses are temporary and are not retained. Route responses remain estimates and include the requested profile and retrieval time. Straight-line distance is a local Haversine calculation with an explicit `great-circle` method and no travel-time field. There is no nearby-place source today.

The client reuses Phase 7's Google Maps and Mapbox browser map presentation and the OpenStreetMap embed fallback. Destination discovery lets a user select a returned nearby destination to update the map panel; trip details show the trip point only to the creator/current active members and otherwise use the public destination point. OpenStreetMap attribution is shown alongside the fallback map. Map rendering does not imply route lookup availability.

`MAPBOX_SERVER_TOKEN` is a server-only secret. `MAPS_PROVIDER_TIMEOUT_MS` defaults to 4500 ms and is clamped between 500 and 10000 ms. Existing `VITE_GOOGLE_MAPS_API_KEY`, `VITE_MAPBOX_ACCESS_TOKEN`, and `VITE_MAP_PROVIDER` only configure browser rendering. Restrict browser keys to production origins and the minimum APIs needed. `CLIENT_URL` controls the allowed CORS origin; configure it per deployment. The built-in OpenStreetMap iframe fallback does not provide live routing or place search.

Nearby requests do not enter the destination process cache, provider lookups are not cached, and the app does not persist browser geolocation. Trip coordinates are omitted from public detail serialization. Application logs contain neither provider URLs nor coordinate query values. Rate limits use the existing in-memory limiter, so multi-instance deployments should configure a shared limiter store to enforce one global provider quota. There is no location Socket.IO channel; any future real-time location channel would require separate authorization and a shared Socket.IO adapter across instances.

Database-backed geospatial behavior must be verified against a dedicated `MONGODB_TEST_URI`. The optional suite uses a separate `${database}_phase16_geo_test` database and checks real `2dsphere` query behavior. Provider integration additionally requires a valid deployment token and provider account; unit tests use mocked provider responses and do not verify live quotas or credentials.
